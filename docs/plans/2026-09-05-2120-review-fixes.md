# コード全体レビューで見つけた 3 点の修正（リーク・DECCKM 自前パーサ・復帰時の 3 秒待ち）

## 概要・やりたいこと

Swift 全ファイルと依存（Citadel 0.12.1 / SwiftTerm 1.20.0 の実装）を読んだレビューで、「直すコスパが確実に高い」と判断した 3 点だけを直す。

1. **端末画面を閉じるたびに `PTYSession` / `SwiftTermSurface` / `TerminalView` がリークする**（バグ）
2. **DECCKM（アプリケーションカーソルモード）を出力バイト列から自前追跡しているが、SwiftTerm が状態を public に出しているので丸ごと消せる**（設計・性能・潜在バグ）
3. **バックグラウンドから復帰するたびに 3 秒の生存判定を待っている可能性が高い**（UX。実機で「復帰 → 接続」の秒数を測って確定してから直す）

他に見たが見送ったもの（影響が小さい・設計上の意図）は本 plan の対象外: 用途ごとの SSH 接続、再接続中の入力破棄、一覧 exec のタイムアウト無し、認証失敗時の無限再接続、`firstToFinish` の理論上の競合、`(settings, identity, knownHosts)` の 3 つ組、`PTYSession` のテスト不能。

## 前提・わかっていること

### 1. リーク

- `TerminalScreen.wireUp()`（`MobileIDE/Features/Terminal/TerminalScreen.swift:216-227`）のクロージャは View 構造体ごと捕まえる。構造体には `@State` の箱（`StoredLocation`、参照型）が入っているので、`surface.onInput` → 箱 → `session`、`session.onOutput` → 箱 → `surface` の循環になる。`network.onChange` も同じ経路で `session` を掴む
- SwiftTerm の `TerminalView` は `CADisplayLink(target: self, ...)` を持ち（iOSTerminalView.swift:682）、`updateUiClosed()`（同 765。`link.invalidate()` と点滅停止）を呼ばない限り DisplayLink が view を握って解放されない。このアプリはどこにも呼んでいない。Metal は既定オフなので残るのは CoreGraphics 側のバッファと DisplayLink（描くものが無いときは `isPaused`）
- `terminalDelegate` は `weak`（iOSTerminalView.swift:124）なので delegate 経由の循環は無い
- `updateUiClosed()` は v1.20.0 の checkout で `public`（iOSTerminalView.swift:765）。**開き直す対（`updateUiOpened` 相当）は無く、`setupDisplayUpdates()` は internal**なので、一度 tearDown した surface は描画を再開できない。この画面は NavigationStack の pop で消える（同じ identity で onAppear が再来する経路は無い。PhotosPicker のシートでは `onDisappear` が走らないことは、既存の `session.close()` が添付中に走っていないことで裏が取れている）
- `SwiftTermSurface` が deinit しても `TerminalView` が解放された証明にはならない（surface → view は一方向。DisplayLink が view を掴んでいても surface は死ねる）。`updateUiClosed()` の効きは view 自体の解放で見る
- `@State private var session = PTYSession()` の初期値は `TerminalScreen` 構造体が作られるたびに生成され、SwiftUI が既存の箱を持っていれば捨てられる。捨てられた個体も deinit するので、目印行には `ObjectIdentifier` を入れて「実際に配線された個体」と突き合わせる
- 実測はしていない（構造上は確実）。修正の検証は `deinit` の目印行と view の weak 参照で行う
- 目印行の収集は `console-run.py --until NEVERMATCH --timeout <秒>` で行う（`--until` は一致した瞬間にプロセスを止めるので、複数行を待つときは一致しない文字列を渡して timeout まで流す。`verify-reconnect.py` の `App` も同じやり方）。stdout はパイプで全バッファなので目印行は必ず `print` + `fflush(stdout)`

### 2. DECCKM

- `SwiftTermSurface.swift:16-19, 52-67` のコメント「SwiftTerm 1.20 は Terminal（applicationCursor）を public に出していない」は誤り。DerivedData の checkout（tag v1.20.0）の `Sources/SwiftTerm/Apple/AppleTerminalView.swift:378` に `public func getTerminal() -> Terminal` があり、`#if os(macOS) || os(iOS) || os(visionOS)` の中（iOS で有効）。`Terminal.applicationCursor` も `public var`（Terminal.swift:408）。2026-09-04 の plan ログ「`getTerminal()` は無い」は `gh api` で見た先が違っていたと思われる
- `TerminalView.feed(byteArray:)` は `terminal.feed(buffer:)` を同期で呼ぶ（AppleTerminalView.swift:2809-2814）ので、feed 直後に読めば値は最新
- 自前パーサの副作用: 出力チャンクごとに `feedTail + Array(bytes)` で全コピー、ESC 1 バイトごとに 5 要素の配列生成。`RIS`（`ESC c`）で SwiftTerm 側がモードを戻すケース（Terminal.swift:959）は自前パーサでは追えない
- 既存の確認手順: VERIFY.md「キーボードバー」節の `printf "\e[?1h"; cat -v` + `PRESS_KEYS=up` → `^[OA`（VERIFY.md:297-298）
- tmux はペイン側の `ESC c`（RIS）や DECCKM を自分で解釈し、クライアントには自分の判断で `ESC [ ? 1 h/l` を送り直す。したがって **RIS の経路は tmux 越しの自走では検証できない**（自前パーサでも tmux が送る `?1l` を拾って正解に見える）。RIS とチャンク境界は `MobileIDETests`（`TEST_HOST` 付きでアプリのコードと UIKit が使える）で `SwiftTermSurface` に直接 feed して見る

### 3. 復帰時の 3 秒

- Citadel にクライアント側 keepalive は無い（ソース全体に該当なし）。復帰時の生死は `verifyAlive()` の `true` exec が 3 秒（`ReconnectPolicy.probeTimeout`）で返るかで決める
- ホストの sshd は `ClientAliveInterval 15` / `CountMax 3` で、無応答の接続を 60 秒超（Air 実測 75 秒）で切る。iPhone が suspend 中に切られると、サーバーの FIN/RST は Tailscale のトンネル停止中に落ちる可能性が高く、端末側からは「無音の死」になる → 復帰のたびに 3 秒の probe + 1 秒の再接続を払っている疑い
- 判定方法: 実機で 90 秒・5 分バックグラウンドにして戻し、「復帰 → `TERMINAL connected`」の秒数を測る。3 秒以上かかる回があれば該当（`probe dead` 経路）。全回 1 秒台（RST が届いて即 `lost`）か `probe ok` なら該当せず、この項目は不要。復帰時は Citadel の `onDisconnect` と `verifyAlive()` が同時に走り順序は決まらないので、ログの順序でなく秒数で判定する
- 直し方: バックグラウンドに入った時刻を覚え、復帰時に経過が閾値を超えていれば probe を飛ばして即再接続。閾値は 60 秒（15 × (3 + 1)。サーバーが切り始める最短）。誤って生きている接続を張り直しても `-D` で attach し直すだけで害はない
- 復帰時は `NetworkPathObserver` の `onChange` と `scenePhase == .active` のどちらが先に `verifyAlive()` を呼ぶか決まらない。先に probe が始まって `probing == true` になると 2 回目が `guard !probing` で弾かれて速い経路を逃すので、**「バックグラウンド経過が閾値超」の判定は `probing` より先に、誰が呼んでも効くようにする**。`lost()` が `generation` を進めるので進行中の probe の結果は捨てられる
- `backgroundedAt` は `verifyAlive()` の入口（state の switch より前）で読み取りと同時にクリアする。`.running` 分岐でしか消さないと、バックグラウンド中に落ちて `.reconnecting` → `retryNow()` に行った場合に記録が残り、後で `running` に戻った接続を `network.onChange` が何分も前の記録で切ってしまう
- `lost("stale after background \(N)s")` の N は整数秒（`Int(elapsed.components.seconds)`）。シナリオの文字列一致に使う
- 自走では DEBUG の起動オプションで「N 秒前にバックグラウンドに入ったことにして復帰」を再現する（速くて安定する）。背面に回す経路自体は `simctl launch` で別アプリを前に出せば起こせる（実装レビュー 1 回目で実測。ログ > 方針変更）
- 決定: `probeTimeout` の短縮（3 秒 → 1 秒）ではなく閾値方式を採る（1 回目で決定）。短縮しても復帰のたびに 1 秒は払い、モバイル回線で生きている接続を誤判定するリスクが上がる。閾値方式は経過時間だけで決まり、外しても `-D` で attach し直すだけ。`probeTimeout` は触らない
- 決定: バックグラウンド中（`.background` 〜 `.active` の間）は `verifyAlive()` を何もしない（実装レビュー 1 回目で決定）。`NetworkPathObserver` はバックグラウンドの実行猶予中も生きていて、ロック直後の経路変更で `verifyAlive()` が呼ばれると記録を 0 秒として消費し、`probing` が立ったまま suspend して復帰時に probe 待ちへ戻ってしまう。`enterBackground()` でフラグを立て、`.active` の `enterForeground()`（実際の経過秒を `TERMINAL resume background=Ns` に出す）で下ろしてから `verifyAlive()` を呼ぶ
- 決定: 60 秒超の復帰は生きている接続でも `-D` で張り直す。Mac 側が同じ tmux セッションに attach していれば detach される（実装レビュー 1 回目で決定）。`-D` は端末を開くたび・再接続のたびに既に効いているので、復帰がそこに加わるだけ。Mac と同じセッションを共有する使い方は VERIFY.md が避けるよう書いている。使い勝手で困ったら閾値を上げるか `-D` の条件を見直す
- 決定: 実機の「修正前の秒数」計測は飛ばして実装を入れたまま Phase 4 で判断する（実装レビュー 1 回目で決定）。修正前の 3 秒はシナリオ 3 の実測（`probe start→dead=3.1s`）が根拠
- 決定: ホスト側の `ClientAliveInterval 15` / `CountMax 3`（`scripts/host-setup.sh`）は維持する（1 回目で決定）。目的は切れた sshd-session と tmux クライアントの掃除で、VERIFY.md「ホスト」節に理由がある。アプリ側の `staleAfterBackground` の doc コメントから `scripts/host-setup.sh` を名指しで参照し、片方を変えたらもう片方を見直すことを書く
